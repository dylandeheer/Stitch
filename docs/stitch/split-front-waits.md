# Split front wait measurements on Stitch 4

Base 72afed7463c79f307d65209fdabcb520538cf13c. The front-waits.patch SHA-256 is b0977fedb3272b3011649797be1bfa426ac43ed7b41d6f30d1c766e0bc646953. The isolated patch changes gpu_split.cpp only. GpuSplit, the ring format and fast Maxwell engine configuration stay outside the diff.

## Capture on a normal build

Set STITCH_SPLIT_WAIT_TRACE=1 at launch and STITCH_SPLIT_WAIT_TRACE_FILE to a local path. Leave its file absent until the target scene, then create it for one ten-second sample. The probe stops after a completed wait or frontend poll reaches its deadline. A wait already running at the boundary is included in full. The log prints actual wall_ns. The marker must be observed absent to arm another capture. With no marker path, it captures once at split startup. Leave EDEN_NX2_GPU_PROFILE off. The front polls the marker in its existing outer command loop, at most once per 250 ms and once per 64 calls. Drain, WaitFor, Backoff and Execute perform no file I/O.

One line per touched site follows “Split front wait end”. Every call and initially unresolved target is counted. wait_ns includes publishing and front waiting, including descheduling. park_ns is nested inside wait_ns and measures actual atomic-wait calls, including immediate returns. The histogram upper edges are exclusive at 2, 10, 50, 250 and 1000 μs, with a last bucket for at least 1 ms. pending_words sums initial target distances in ring words. The ring space row counts the slow reserve path and uses its existing cached-consumed test; it can find room on the first fresh load. No addresses or payloads are logged.

The sample retains 16 fixed rows. The clock is read twice per unresolved wait and twice per actual park, apart from the bounded outer-loop polls and finalization. Disabled mode performs zero diagnostic clock calls. Compare instrumented and adjacent quiet windows before reporting gameplay performance.

Native syntax verification used the project's compiler database. verify.py replays the actual production wait methods against controlled releases, captures calls and memory orders of synchronization atomics and checks return values, publish positions and pause counts. Original, probe-disabled and probe-enabled paths matched all 16,407 synchronization observations, with 16,388 pauses. The test checked a 0.9 ms park, ready calls, ring pressure, threshold bins, a completed one-shot and rearm. Removing the wait or misclassifying its reason failed the negative controls. Publish, Execute, BackLoop and ReserveSlow bodies matched byte-for-byte. No Steam operation or Linux build was run by this reviewer.

## Decisions after the sample

1. If long waits dominate and most wait_ns precedes parking, test an earlier transition into the existing front_wake sleep handshake, scoped to the worst reason at first. Preserve the 64-bit ring target, publish, position recheck and lost-wakeup sequence. Drain/WaitFor currently execute up to 16,384 pause iterations before that handshake, and the back spins 8,192 times when apparently idle. Change one side at a time. Measure front CPU and route/present times.
2. If acquire or fence release dominates, distinguish initial acquires from suspended-channel retries before attempting #805's fence shortcuts. CanResumeAcquire drains and reads even for latched releases. A completed latch alone does not prove all prior back work is irrelevant to the next front-owned list, macro read or cache flush. A larger candidate would park only the channel, process other eligible channels, and require back-owned read/release completion plus the existing latched-value semantics. Preserve CPU-written releases, cross-page aliases, remaps, teardown, driver progress and notification-before-park.
3. If macro DMA read and macro DMA flush dominate, distinguish waiting for ring consumption from the buffer/query landing. Combined DMA handoffs previously failed to improve the hardware ABBA, and the writer-frontier still waited in 99.5% of reads and regressed mean FPS. #805's completed demand-copy data is relevant only when it covers those actual reads. If list sync/list flush dominates, correlate command-copy ticks and list readiness first. Predicted QMD or semaphore placeholders affect guest-visible memory.
4. The six CPUCore JIT percentages do not identify guest spin code. Linux x64 Dynarmic already emits a perf map when PERF_BUILDID_DIR is set before JIT starts. Using /tmp gives the conventional /tmp/perf-<pid>.map with a64_<guest-PC>_fpcr<flags> block names. Clearing the JIT truncates/reopens that map. Snapshot it near the short sampling window. Entries are written unbuffered under a mutex, so run this separately from timing ABBA. Correlate repeated guest PCs with private offline instructions before identifying a poll loop. GetCNTPCT already applies two x86 pauses to sufficiently close consecutive counter reads by default, controlled by EDEN_NX2_CNTPCT_PAUSE. A64 WFE/WFI/YIELD callbacks return after tracing and cannot classify arbitrary loops. Renderer.pin_gpu_threads is false in the measured profile. Enabling it would reserve two physical cores for GPU front/back and constrain six guest vCPUs to the other four physical cores on this host. Test that only if scheduling traces identify contention.
