# Native Mac OoT setup review

Reviewed tracked source at `562dfa90e1e678966f168b5813850e43e27f9d0b` on branch `stitch/macos-20261111`. Read-only source/dependency review; no source edits, builds, app launches, SSH, captures or device configuration changes. This does not establish game compatibility or FPS.

## Required setup and validation

1. **Build arm64 Dynarmic, not Rosetta or NCE.** `CMakeLists.txt:336` defines `HAS_NCE` only for arm64 Linux/Android. `src/common/settings.h:261` selects Dynarmic on this Mac build. There is no Mac Hypervisor CPU backend in this pinned source. Apple Silicon therefore removes the x86 host translation path but does not make this version execute guest code directly. The optional `STITCH_OOT_COMPARE_LINK` shortcut is also Linux/x86-64-only (`arm_dynarmic_64.cpp:471`); carrying its environment variable into Mac has no effect.

2. **Sign and test the real JIT executable after packaging.** Dynarmic's ARM64 address space owns `oaknut::CodeBlock` (`src/dynarmic/src/dynarmic/backend/arm64/address_space.cpp:27`). The pinned Oaknut dependency allocates `MAP_JIT` executable memory and uses `pthread_jit_write_protect_np` around emission (`.cache/cpm/oaknut/v2.0.3/include/oaknut/code_block.hpp:37,76,85`). Use an explicit `com.apple.security.cs.allow-jit` entitlement on the actual Mach-O executable. If a shell wrapper is made `CFBundleExecutable`, signing only that wrapper/outer app is insufficient to establish that the later `exec`ed Mach-O carries the entitlement. Sign nested libraries/frameworks first, the actual program with the entitlement next, and the outer app last, then run `codesign --verify --deep --strict`. The release workflow currently makes entitlement use conditional on an absent `dist/eglantine.entitlements`; it is not proof that a packaged JIT works. A non-hardened ad-hoc program may work without an explicit entitlement, so missing entitlement alone is not a reproduced failure here. Do not add Hypervisor entitlement: this source has no corresponding Mac backend. Oaknut checks `mmap` only against `nullptr`, not `MAP_FAILED`; an allocation/entitlement failure can become a first-emission crash instead of a useful allocation error.

3. **Bundle and qualify the actual MoltenVK library.** `src/video_core/vulkan_common/vulkan_library.cpp:131` tries `LIBVULKAN_PATH`, then the app's `Contents/Frameworks/libvulkan.1.dylib`, then `Contents/Frameworks/libMoltenVK.dylib`. The CMake Apple target embeds the pinned MoltenVK dylib. Ensure the finished app really contains an arm64 library at one of those exact bundle paths and that its own dependencies resolve in the bundle/system. Avoid leaving `LIBVULKAN_PATH` inherited from an unrelated developer environment. The existing source already adapts several unsupported MoltenVK features, render-target typing, four-byte input strides, primitive restart, pipeline-cache retention and transfer handling.

4. **Do not carry Linux extended-dynamic-state selection into Mac settings.** `src/common/settings.h:820` defaults `dyna_state` to `Disabled` on Apple, while Linux defaults to `EDS2`. `src/common/recommended_settings.h:60` explicitly documents black screens with MoltenVK when extended dynamic state is enabled. In a copied profile, set `Renderer/dyna_state=0`, `dyna_state\default=false`; ensure the game's effective per-title selection uses that global value or is explicitly zero. Fresh Mac configuration already has the correct default. This is the strongest concrete settings compatibility gate found.

5. **Keep complete geometry rendering through the compute mesh path.** `src/video_core/vulkan_common/vulkan_device.cpp:1773` enables native mesh only when both task and mesh features exist; `EDEN_NX2_FORCE_MESH_FALLBACK` disables that extension. A normal MoltenVK device lacking native mesh automatically uses the compute fallback. Keeping the explicit fallback variable for this first comparison is reasonable; clear `EDEN_NX2_NO_MESH`, `EDEN_NX2_NO_MESH_EMULATION`, and `EDEN_NX2_NO_TASK_EMULATION`. Leave optional bounded-mesh lookup off for the first full-game test. A tiny mesh primitive test on the same Mac does not establish all game geometry/lighting correctness.

6. **Paired tensor operations are capability gated.** `src/video_core/renderer_vulkan/vk_pipeline_cache.cpp:715` selects the 16×16×16 KHR path only when the device advertises the required support and the other tensor path is unavailable. `STITCH_PAIR_TENSOR_COLUMNS` passes through that capability gate. Setting the variable does not create Metal tensor support; without the required capability the ordinary shader path remains. Do not assume the AMD Steam Machine's tensor gain transfers to M1 Max. Use startup feature logs to record which path was selected.

7. **Use XDG isolation because the Apple GUI resets its working directory.** `src/yuzu/main.cpp:156` changes cwd to `GetBundleDirectory()/..` before GUI initialization. Although the generic path manager checks `cwd/user`, a launch wrapper's earlier `cd` therefore does not select a Mac portable profile reliably. Set all three `XDG_CONFIG_HOME`, `XDG_DATA_HOME` and `XDG_CACHE_HOME` in a native launcher before executing the actual bundled payload; `GetDataDirectory` honors these variables on Apple (`path_util.cpp:384`). Check that the app bundle's parent (`~/Applications` for the planned install) has no `user` directory, because that portable directory would override XDG. Keep profile roots outside the signed `.app`. Rewrite copied `Data%20Storage` paths; otherwise the Steam Machine's absolute NAND/load/save paths survive. Copy the matching NAND/account data and save together. Start a Mac-native input configuration: Steam's virtual-controller GUID/device selection is not a portable physical-controller binding. Use the original local NUP rather than duplicating its 23 GB, and keep driver-specific shader caches separate.

8. **Mac limits still require a real scene test.** The compute path clamps a translated program's shared-memory size to the MoltenVK device limit (`vk_pipeline_cache.cpp:3177`). That is existing code, not evidence that the original shader's accesses fit. Preserve any resulting warning/hash privately and verify doors, foliage, lights, transitions, audio and controls in the real game. No new source defect is proved from that clamp alone. Keep new predictive readbacks, CPU warmup and profiling off for the first ordinary comparison.

9. **The source explicitly handles Apple 16 KB host pages; qualify it at boot.** `Settings::IsFastmemEnabled` returns true on Apple (the Linux/arm64 4 KB-only restriction does not apply). POSIX HostMemory creates a shared backing object with `shm_open`, immediately unlinks it and uses an unlinked temporary-file fallback (`host_memory.cpp:630`). When host pages differ from the guest's 4 KB, it creates per-guest-page state and maps a host page only when its guest pages can be represented together (`host_memory.cpp:695`). Thus a blanket fastmem disable is not justified just because M1 uses 16 KB pages. Expected startup evidence is `Fastmem maps 0x4000 byte host pages whose guest pages are contiguous`; investigate any `Can't emulate ...`, `mmap failed`, `ftruncate` or private-backing warning. Dynarmic registers a Mach bad-access exception server for fastmem fallback; its constructor checks each `mach_*`/`task_set_exception_ports` call and must finish during a real guest boot. No Hypervisor entitlement is used for that Mach exception path. These code paths are present, but were not executed in this read-only review.

## Suggested acceptance evidence

- The packaged Mach-O and MoltenVK are arm64; code signatures verify after the final bundle modifications.
- No Homebrew/build-prefix Qt, nxformat, codec or other runtime dependency is accidentally required outside the finished app.
- The running log reports source `562dfa90`, Apple/MoltenVK, Dynarmic, isolated XDG Mac paths and disabled extended dynamic state.
- The owner launches a normal scene from the copied save and confirms complete geometry, lighting, sound and input.
- A later quiet frame-time sample is taken after initial pipeline compilation; no stable-60-FPS or Mac-versus-Steam-Machine gain is inferred from build/launch success.

No web research was needed for these findings: the code, pinned dependency and release workflow are the primary evidence. No game assets or private instruction/shader data are included in this report.

## Later reproduced compiler/runtime gate

The clean single-SDK Apple Clang build subsequently exposed typed standard-exception matching failures under the project's `-fno-rtti` policy. Root reproduced the issue outside the application using `std::stoi("invalid")` and a `std::invalid_argument` handler: ordinary RTTI exits 0, no-RTTI terminates uncaught (134), also with Homebrew Clang 21. The two Apple-only CMake adaptations select RTTI for app/core/tests and remove Dynarmic's explicit no-RTTI override; other platform policies remain. Current generated commands contain no project/Dynarmic no-RTTI flags. The full native rebuild and nine suites must pass before packaging/launch. See `RTTI-REVIEW.md` for flag scope, actual inheritance and the remaining vendor Cubeb exception-free boundary. No test assertions were weakened by this RTTI adaptation.
